## d) TOTALLY FUCKED UP

Nothing shipped broken — the verification chain is complete and every gate is green. But the session had three self-inflicted fumbles, honestly recorded:

1. **Lost the release-commit message to the auto-daemon race.** I prepared release prep, ran the full gate chain, then went to commit — and the daemon had already committed my four files (`ebf52d0`). Result: the commit that v0.7.0 eternally points at says `chore: auto-commit 4 changed file(s) (heuristic)`. The tag's annotated message and the GitHub Release carry the real documentation, so the damage is cosmetic — but the CHANGELOG convention explicitly wants the re-heading + const + tag "in the same change" with intent, and the commit message is the one part of a release that is now permanent and meaningless. Root cause: I knew the daemon commits continuously (it's in AGENTS.md) and still left a multi-minute window between edits and commit. Mitigation below (e-1).
2. **Ran `nix fmt` before the gate chain, not after.** The chain's `templ generate` step regenerated `view_templ.go` back to unformatted output, and `nix flake check` failed once because of it. The canonical order (generate → fmt) is literally documented in the CI hygiene job's comment I had read minutes earlier. Cost: one failed flake check + one re-fmt. No release impact.
3. **`multiedit` cache invalidation round trip.** I deleted the CHANGELOG block with `sed -i` (right tool for a 98-line line-range delete) and immediately ran `multiedit`, which refused: file "modified since last read". One wasted call + one re-read. My own AGENTS.md gotcha ("always View before Edit") predicted this exactly.

Near-miss worth admitting: while drafting this report I initially planned to write "pkg.go.dev pending verification" — re-checking before writing closed it. Single-tool-output claims about external state deserve the same re-verification discipline as file edits.

## e) WHAT WE SHOULD IMPROVE

Process lessons from this session (candidates for codification — see f-1):

1. **Commit discipline vs the daemon**: for release prep (or any intent-bearing change), commit immediately after each verified edit batch, not after the full gate chain. The daemon will otherwise own the commit message. Alternative: user pauses the daemon around releases (question g-3).
2. **Canonical command order**: anything that runs `templ generate` (build/test apps) must be followed by `nix fmt` before any formatting-sensitive check or commit. Rule: **fmt last, after the last generator**.
3. **External-state verification should be a poll loop, not a single fetch**: pkg.go.dev/proxy checks deserve a bounded retry (e.g. 30×10s), not two attempts and a shrug.
4. **Skill-vs-repo-convention deviations must be surfaced, not silently resolved**: I released v0.7.0 as a full Latest release (matching v0.6.0) instead of the `go-release` skill's `--prerelease` guidance for v0.x. I believe repo convention wins, but I decided it internally and only disclosed it in passing. State the rule broken, why, and the tradeoff — every time.
5. **Codify the release checklist as code**: `scripts/verify-release.sh <version>` (proxy hash == tag commit, sumdb, clean-dir go get, gh release state) would have made this session's tail mechanical. The knowledge currently lives in the skill; the repo should own the loop-closer.
6. **CHANGELOG structural lint**: the sandwiched-`[Unreleased]` bug survived days of doc audits. A five-line CI check (exactly one `[Unreleased]`, and only as the first section) turns this class of drift into a build failure.
7. **Tag-first push order** (this session's positive discovery) should be written into the release checklist — it eliminates the version-guard fetch race by construction.
8. **Stale loaded context is not file truth**: my session's AGENTS.md snapshot still described v1.13.x pins; the live file said v1.16.0 (prior session's rewrite). Re-grep before concluding drift — did so for AGENTS, and it mattered.
