## Straight Answers to the Three Questions

### What did you forget?

1. **`bash scripts/pre-push-checks.sh`. The single biggest miss.** The script exists precisely for this moment — its own header says *"so a red job is discovered at the desk instead of after a push"* — and its check #1 is **character-for-character the drift guard that failed CI**. One command before tagging and v0.8.1 would not exist. It is not in `docs/release-checklist.md` §4's gate list, and I did not notice that gap either — I ran the listed gates and never asked what the desk gate consolidates.
2. **The recount when editing FEATURES.md.** I edited the Released row and never glanced at the Test-suite row five lines up with a stale count. The guard's entire job is to force that recount; I made the guard do its job from CI instead of at the desk.
3. **Wait for CI green before `gh release create`.** I published the v0.8.0 release page while CI was still running; it went red 90 seconds later. The published page now permanently points at a red-CI commit.
4. **Eyeballing the screenshots before pushing.** Only done at 07:00, after the fact (both are fine — truth strip renders in light and dark — but that was luck, not process).
5. **Verifying the `Latest` flag.** My check used a nonexistent JSON field (`isLatest`), errored, and I never re-verified with a working command.

### What could you have done better?

1. **Run the desk gate before tagging** — that's items 1+2 above; everything else is commentary.
2. **Stop piping gates through `tail`.** `nix flake check | tail; echo $?` reports tail's exit code. I committed the exact "pipeline masking" failure class documented in AGENTS.md, in-session, and almost declared a failing gate green. Should be `cmd > log 2>&1; rc=$?` every time, no exceptions.
3. **Don't trust a single tool when it contradicts a second one.** `nix fmt` said "0 changed" while the treefmt check drv said "2 changed". I re-ran the masked pipeline instead of immediately investigating the contradiction. The contradiction was the signal; the stale treefmt cache was the cause (`nix fmt -- --no-cache` tells the truth).
4. **Tighter edit→commit windows.** The AGENTS.md lesson ("commit intent-bearing batches immediately, the daemon eats what sits uncommitted") was in front of me and I still let the release edits sit for ~10 minutes while fighting the flake check. Lost both races, needed two amends. Amends worked (commits were unpushed and contained exactly my files), but that's recovery, not discipline.
5. **Publish the GitHub Release only after `verify-release.sh` passes** — split the script's release-page check from the rest if the ordering is awkward.

### What could you still improve?

See section (e). The short version: the release ritual has one missing step (desk gate), one ordering fix (CI before release page), and one structural irritant (daemon racing) that needs a decision from you, not more willpower from me.

### Did you lie to you / distort?

No lies. Two soft spots, both disclosed but worth restating:
- **"Browser suite green"** for the v1.17.0 audit: the run printed `ok 13.011s` without `-v`, so a silently-skipped test (e.g. the axe audit skips when cdnjs is unreachable) would be invisible in that line. The pattern itself is complete — all 17 browser tests are `TestBrowser_*`, so `-run TestBrowser` covered the full suite — but *ran vs skipped* is unproven from that output alone.
- **v0.8.0 is a release whose release-commit CI is permanently red.** `verify-release.sh v0.8.0` can never be all green (check 5). The module content is fine and v0.8.1 is the verified head, but the v0.8.0 release page should eventually say so (section f, item 3 / question 2).

## e) WHAT WE SHOULD IMPROVE

1. **Make the desk gate part of the ritual.** Add `bash scripts/pre-push-checks.sh` to `docs/release-checklist.md` §4 as a first-class gate — and as step 0, *before* any edits, so a stale-count bomb surfaces before work starts, not after tagging.
2. **Order the publish after the proof.** §6 should read: verify-release green (minus its release-page check) → CI green on the release commit → *then* `gh release create`.
3. **Never pipe gates.** Codify: gates run as `cmd > log 2>&1; rc=$?`. The `set -e` + pipefail lesson exists; make the release checklist say it explicitly for `nix flake check`/`verify-release.sh` invocations.
4. **Retrain `nix fmt` trust.** Document the stale-cache failure mode + the `nix fmt -- --no-cache` recipe (AGENTS.md gotcha + checklist). A formatter that says "0 changed" while the check drv says "2 changed" is a split brain in tooling.
5. **Daemon vs release commits** — needs your input (question 1). Amending works but is a workaround; a pause mechanism or a release-window protocol would remove the race class.
6. **Sweep adoption is mechanical — partially automate it.** Six sweeps means the *adoption* (pins + README + FEATURES + checklist wording) could be a script that does the 4 file edits mechanically, leaving browser suite + commit human/agent-gated.
7. **Publish-facing pages are permanent — treat them that way.** Release pages get created only after full verification; fixes to published pages need an explicit policy (question 2).
8. **Verbose test output for release audits.** Release-gating test runs should use `-v` (or count `--- PASS` vs `--- SKIP`) so "green" is distinguishable from "skipped".
