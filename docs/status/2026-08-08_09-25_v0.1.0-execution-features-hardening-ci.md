## G) Questions

### 1. D2: Replace directives — should we tag the upstream repos NOW?

go.mod has 6 `replace` directives pointing to local sibling repos. This blocks
`go get` for external consumers. The templ-components nonce fix from this
session is committed locally but not tagged upstream. **Do you want to tag
go-health, templ-components, go-datastar, and go-sse on GitHub so we can remove
the replace directives and make the package consumable?** This is the single
biggest blocker to a public v0.1.0 release.

### 2. D3: GOEXPERIMENT=jsonv2 — accept, fork, or gate?

Every Go command requires `GOEXPERIMENT=jsonv2` because go-sse uses
`encoding/json/v2`. The CI workflow sets it. The flake.nix devShell sets it.
But external consumers will hit cryptic compile errors without it. **Do we
accept this requirement (and document it loudly), fork go-sse to remove the
dependency, or build-tag gate the SSE code so consumers who only want HTML pay
no cost?** Each path has different tradeoffs for maintenance burden vs.
adoption friction.

### 3. Should FEATURES.md and ROADMAP.md be auto-regenerated or manually maintained?

These files went stale within one session. FEATURES.md actively lies about the
project state now. **Do you want a docs-health skill run to rebuild these from
the codebase, or do you prefer to maintain them manually?** The auto-regenerate
approach catches drift but may lose nuance; manual maintenance keeps intent but
requires discipline (which clearly failed here).
