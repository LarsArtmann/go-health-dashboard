go-health — Adoption & Utilization Audit

How well does go-health-dashboard consume its own health-checking SDK? Verdict: an exemplary, textbook composition — with one real wire-format drift to fix today and a handful of cheap alignments with go-health v0.3.0's newer surface.

00Summary

go-health-dashboard consumes go-health the way the Go community tells people to: a narrow consumer-side Prober interface, lock-free cached reads as the single data source for every write seam, go-health's own three kubelet handlers passed through untouched, and the aggregate/federation surfaces composed in without the dashboard knowing they exist. Nothing is re-implemented that go-health already exports — except two things, and one of them matters.

The bottom line The dashboard re-implements go-health's readiness-JSON path and dropped json.Deterministic(true) while doing it: both the /health JSON response and the /health/export JSON serialize their check maps in random order per response (verified: 115/200 marshals identical). go-health's own handlers pin deterministic sorted keys, and the dashboard's stated contract is to stay byte-stable with them. Two one-line fixes restore it. Everything else is polish: adopt Status.Rank() where severity is compared, and surface Response.InstanceID in the federation hub. The version question resolved itself mid-audit: go-health v0.4.0 was tagged 2026-09-22, a fleet dependency sweep landed it the same day, and it was verified deliberately (green gate chain) rather than reverted.

◆What's already excellent

Nine of eleven applicable capability areas are fully leveraged. These are the patterns a reviewer would hold up as the reference for "how to consume an SDK".

+
Consumer-side Prober interface dashboard.go:28-41 defines exactly the five methods it needs (CachedResponse, RefreshInterval, three handler getters). *health.Probe, aggregate.Aggregate, and federation.Federation all satisfy it structurally — one dashboard renders single probes, merged in-process probes, and N remote instances with zero knowledge of the concrete types. integration_test.go and cmd/health-hub prove all three compositions.
+
CachedResponse() as the one data source currentResponse() (dashboard.go:158-160) is the single read seam; the view model, metrics, fingerprints, trend ring, and evidence log all share one snapshot per tick. Lock-free, ~0.03 ns/op per go-health's benchmarks. The shutdown overlay in CachedResponse means the dashboard gets fail-closed 503s for free.
+
SanitizeResponse at the choke point Applied once in currentResponse() (dashboard.go:159), so every write seam — JSON, webhook, SSE patches, metrics labels, CSV — inherits valid UTF-8. Exactly the fuzz-found hardening go-health built for jsonv2 consumers.
+
go-health's own handlers served untouched The kubelet endpoints wire LivenessHandler/ReadinessHandler/StartupHandler verbatim (no re-marshaling), deliberately outside WithMiddleware so authenticated dashboards can't break kubelet probes. RefreshInterval() drives the default push cadence (resolvePushInterval, dashboard.go:141-151) instead of a second tunable drifting from probe reality.
+
v0.2.0 check metadata fully surfaced Check.Since powers row age stamps, evidence tooltips, and survives the federation wire; Check.DurationNanos powers the rendered duration line and the dashboard_health_check_last_duration_seconds series with go-health's omitzero discipline mirrored (metrics.go:104-106, trend.go:29-35).
+
Status constants mapped directly status.go:22-55 maps StatusPass/StatusWarn/StatusFail straight to display.Badge* and feedback.Feedback* constants — no stringly-typed bridge, no deprecated AlertType alias.
+
Federation + aggregate composed, not re-built health-hub is 30 lines around federation.New (main.go:113-123); the example uses aggregate.New. The dashboard's GroupBySource mode exists precisely because go-health namespaces keys source/check — the two modules co-evolved instead of one duplicating the other.
+
Content negotiation is the sanctioned layer The 45-line Accept parser (handlers.go:46-91) looks like duplication but isn't: go-health's docs/content-negotiation-design.md §Decision explicitly rejected adding negotiation to go-health and assigns HTML/JSON splitting to this composition layer.
+
Zero-dependency discipline shared Hand-rolled rate limiter and Prometheus exposition duplicate x/time and client_golang — not go-health, which offers neither. go-health's own Prometheus story is "composition + ~40-line writer"; the dashboard's is richer (histogram, webhook stats, public-mode label masking). Consistent policy on both sides of the boundary.

01Findings

Ordered by impact. The first two are real correctness drifts; the rest are alignments with API go-health added for exactly this consumer.

Wire-format drift · High impact · one-line fix

/health JSON serializes checks in random order — the byte-stability contract is silently broken

handlers.go:106 (serveJSON) · go-health handlers.go:196-198 (marshalResponse)

go-health's handlers marshal with json.Marshal(resp, json.Deterministic(true)) — without that option, encoding/json/v2 emits Go maps in unreliable order (verified empirically: 200 marshals of one 4-key map produced 115 identical / 85 shuffled outputs). The dashboard's serveJSON marshals the same health.Response — whose Checks field is a map — with plain json.Marshal(resp). AGENTS.md's contract for this exact endpoint says it "stays byte-stable with go-health's own probe handlers (kubelets and scrapers diff payloads)". Any scraper diffing consecutive scrapes sees phantom check reshuffles that look like flaps. Every other dashboard marshal site (webhook.go:149, introspect.go:112, ratelimit.go:89) already passes the option — this one was missed. 

// Before (handlers.go:106) — Checks map order is random per response
payload, err := json.Marshal(resp)

// After — matches go-health's writeResponse byte-for-byte
payload, err := json.Marshal(resp, json.Deterministic(true))
Fix Add json.Deterministic(true) at handlers.go:106 and pin the ordering in a test (marshal a multi-check response twice through serveJSON and require identical bytes, the same discipline webhook_payload_test.go:89 already applies to webhooks).
Wire-format drift · Medium impact · one-line fix

/health/export JSON has the same nondeterminism in its checks object

trend.go:217 (ExportHandler JSON branch) · payload struct trend.go:42-47

The export payload carries Checks map[string]jsonCheckMeta and is written with plain json.MarshalWrite(w, out). Export is dashboard-owned and explicitly the endpoint consumers are told to diff and extend ("freshness and timing data for JSON consumers"), so shuffled key order between exports defeats the purpose. The trend endpoint (trend.go:153) is unaffected — its payload holds only slices — as is the NDJSON branch (trend.go:227, plain struct rows). 

// Before (trend.go:217)
if err := json.MarshalWrite(w, out); err != nil {

// After
if err := json.MarshalWrite(w, out, json.Deterministic(true)); err != nil {
Fix Same one-line option at trend.go:217; extend the existing trend_endpoints_test.go with a two-scrape byte-equality assertion.
Partial duplication · justified, but document the seam

serveJSON re-implements ReadinessHandler's cached path — correctly, but nothing says so

handlers.go:95-115 · go-health handlers.go:59-77

The JSON branch of /health duplicates go-health's readiness handler line for line: same cache read (CachedResponse overlays shutdown into Status=fail exactly like readiness does, probe.go:657-677), same 503-on-fail mapping, same Content-Type and Cache-Control headers, same sanitize step. Delegating to d.probe.ReadinessHandler() would be wrong — on live-mode probes (RefreshInterval(0)) it evaluates dependencies per scrape, breaking the dashboard's zero-cost-reads contract. So the duplication is deliberate and correct; the only bug it bred is Finding 1 (the dropped option). What's missing is the sentence that keeps the next editor from "simplifying" it in either direction.

Recommendation One comment on serveJSON: "Wire-compatible copy of go-health's readiness handler, cache-read-only so live probes stay free; keep the marshal options identical to health.marshalResponse." Then Finding 1's fix makes "identical" true and testable.
Partially used · Medium impact

Severity ordering re-derived four times; go-health v0.3.0 published Status.Rank() for exactly this

status.go:373-390 (worstGroupStatus) · metrics.go:193-201 (numericHealthStatus) · status.go:232-243 (statusValue) · history.go (trend thresholds)

v0.3.0's changelog: "Status.Rank() is public: the severity ordering (fail 0 < warn 1 < pass 2) behind the merge sites, so consumers merging statuses share one ordering." The pinned snapshot already contains it (verified in aafc76e:types.go) — the dashboard uses none of it and instead maintains four private status→number mappings. The orderings agree; the unknown-status defaults deliberately diverge per site (grouping→warn "must not read as healthy", metrics→-1 "never confuse with fail", trend→0). numericHealthStatus is literally Rank() plus the -1 default; worstGroupStatus's fail-first loop is the exact merge idiom Rank was extracted from. Four places to keep in sync with zero tests tying them to go-health's canonical ordering is drift bait. 

// worstGroupStatus (status.go:376-387), using the canonical ordering
for _, row := range rows {
    switch row.Status {
    case health.StatusFail:
        return health.StatusFail
    case health.StatusWarn, health.StatusPass:
        // keep walking
    default:
        // dashboard-specific: unknown must not read healthy —
        // deliberately stricter than Rank()'s unknown→pass
        return health.StatusWarn
    }
}
Recommendation Where sites compare or encode ordering, derive from Rank() and keep only the local unknown-default explicit; cite Rank() in each comment so a future status-value change upstream surfaces here. Do not collapse the four sites into one helper — their unknown handling is intentionally different.
Missed opportunity · Medium impact for the hub

Response.InstanceID is never surfaced — the federation hub is where it earns its keep

not used anywhere (grep: zero non-test references) · go-health types.go:90

go-health added WithInstanceID "to identify this replica when multiple instances serve behind one load balancer". The dashboard consumes every other response scalar — Version (status.go:212), Uptime (status.go:213), TotalLatencyMs (status.go:214, metrics.go:123), ShuttingDown (status.go:200) — but drops InstanceID. The health-hub merges N remotes where several may be replicas of the same service; showing the instance ID in a group's detail line is the difference between "api is degraded" and "api replica 7f3a is degraded". Treat it as semi-identifying: mask it in public mode the way check names are masked (metrics.go:80-83 pattern).

Recommendation Thread resp.InstanceID into checkGroup/viewModel, render in the group card detail cell when non-empty, mask under WithPublicMode.
Nice to have · Low impact

go-health's combined Healthz() endpoint has no dashboard passthrough

routes.go:4-16 · go-health accessors.go:154

go-health ships Probe.Healthz() — the single-endpoint "should traffic route here?" handler (503 while booting/failing/draining). The dashboard registers the three kubelet probes but not this one, and Prober doesn't expose it, so a consumer can't reach it through the dashboard's route table. Fair to skip for now: the aggregate twin (Aggregate.Healthz()) is still unreleased upstream (go-health CHANGELOG Unreleased), and consumers can wire the probe's handler themselves today. Revisit when the aggregate version ships so the hub can expose one coherent route.

Nice to have · Low impact · example ergonomics

v0.3.0's NewChecks() would shrink the example's probe scaffolding

example/main.go (injector + do.ProvideNamed scaffolding)

NewChecks(map[string]CheckFunc) is the injector-free named-checks constructor: concurrent batches, per-check timing (surfaces as duration_ns — which the dashboard renders), panic recovery, wedged-check abandonment. The example currently builds a samber/do injector to simulate services. Switching the example to NewChecks would demonstrate the lighter integration path, feed DurationNanos through the rendered duration line, and cut scaffolding. Demo-only value; the injector path remains the right one for real samber/do apps.

03Version currency

The audit opened with go.mod pinning the master pseudo-version v0.2.1-0.20260918115637-aafc76e229a5 (2026-09-18) while v0.3.0 (2026-09-19) was already tagged and HEAD sat 16 commits past it. Before the report was finished, go-health tagged v0.4.0 (2026-09-22) and a fleet dependency sweep landed it in go.mod; it was ratified with a green gate chain instead of reverted, since the re-pin to a real tag was already scheduled work. Verified: v0.4.0 is additive for this module — Status.Rank(), federation, NewChecks, Aggregate.Healthz() (which unblocks Finding 6), and upstream determinism work (ADR-006, a sorted-order Prometheus reference) that independently endorses Findings 1–2. One hard edge: v0.4.0's module graph requires go 1.27.1, so the fleet normalize step's go 1.27 downgrade breaks every module load and the directive had to be restored.
