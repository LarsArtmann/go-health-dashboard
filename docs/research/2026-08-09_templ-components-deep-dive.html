00Summary

go-health-dashboard imports templ-components v1.8.0 (the latest tag) and uses 13 of its 116 components across 5 source files (view.templ, status.go, and the generated view_templ.go). The core SSE-first architecture is done right: datastar.LiveRegion, datastar.SDKScript, and explicit HTMXVersion: "" on layout.Base show a team that understood the library's Datastar philosophy. The feedback and badge type mappings correctly use the non-deprecated FeedbackType over AlertType.

However, the dashboard only scratches the surface of what templ-components offers for a status dashboard. It hand-rolls a page header instead of using display.PageHeader, uses raw Tailwind space-y-6 divs instead of layout.Stack, ignores the entire icons package (102 icons), and leaves StatCard's Trend, Icon, and Change fields empty. There are no loading skeletons, no collapsible groups for healthy services, no "last updated" timestamp, and no branded error pages.

The bottom line The foundation is excellent — correct Datastar architecture, right component choices for the core layout. But the dashboard is using templ-components as a basic component shelf, not as a design system. Adopting display.PageHeader, layout.Stack, StatCard enrichment (Trend/Icon), Badge Dot indicators, icons.Icon, loading skeletons, and display.CollapsibleSection would elevate it from "works" to "superb" — all are drop-in or near-drop-in changes with zero new dependencies.

01Current Usage

The dashboard imports 5 templ-components packages (display, feedback, layout, datastar, utils) and uses these 13 components:

dashboard ├── layout.Base + PageProps ├── layout.Container + DefaultContainerProps() ├── layout.ThemeToggle ├── datastar.SDKScript + SDKScriptProps ├── datastar.LiveRegion + LiveRegionProps ├── display.Grid + GridProps (GridCols3) ├── display.StatCard + StatCardProps (Value/Label only) ├── display.Card + CardProps (Title/Padding) ├── display.Table + TableProps ├── display.Badge + BadgeProps ├── display.SimpleEmptyState ├── feedback.Alert + AlertProps (Title only) └── utils.BaseProps (embedded in all props)

The architecture is sound: layout.Base renders the HTML shell with CSP nonce and no HTMX. datastar.SDKScript injects the Datastar runtime. datastar.LiveRegion wraps the health content with data-init="@get('/health/sse')" for real-time SSE updates. The pusher goroutine renders dashboardContent as a Datastar ElementsPatch and broadcasts via sse.Broadcaster. Health status maps to FeedbackType (non-deprecated) and BadgeType constants through explicit switch statements in status.go.

02Missed Opportunities

Powerful features not used anywhere in the project, each solving a real problem in this codebase. Ordered by impact.

Missed Opportunity · High impact

display.PageHeader — hand-rolled duplicate

view.templ:28-36 · display.PageHeader available but unused

The dashboard hand-rolls a header with <h1 class="text-2xl font-bold tracking-tight text-gray-900 dark:text-gray-100">, a subtitle paragraph, and a flex layout to position the ThemeToggle. templ-components ships display.PageHeader(PageHeaderProps{Title, Subtitle, Action}) which renders exactly this pattern: title in the same classes, muted subtitle, and an Action slot on the right. The ThemeToggle would go in the Action slot. This is the textbook "hand-rolled duplicate of a library component" finding.

Recommendation Replace the 10-line manual header with display.PageHeader. 
// Before: 10 lines of manual header (view.templ:28-37)
<div class="mb-6 flex items-center justify-between">
    <div>
        <h1 class="text-2xl font-bold tracking-tight text-gray-900 dark:text-gray-100">{ data.Title }</h1>
        <p class="mt-1 text-sm text-gray-500 dark:text-gray-400">Real-time health monitoring</p>
    </div>
    @layout.ThemeToggle("Toggle theme", data.DatastarNonce)
</div>

// After: 1 component call with Action slot
@display.PageHeader(display.PageHeaderProps{
    Title:    data.Title,
    Subtitle: "Real-time health monitoring",
    Action:   layout.ThemeToggle("Toggle theme", data.DatastarNonce),
})
Missed Opportunity · High impact

layout.Stack — manual space-y divs

view.templ:52, 101 · <div class="mt-6 space-y-6"> instead of layout.Stack

The dashboard uses raw <div class="mt-6 space-y-6"> for vertical layout. templ-components ships layout.Stack(StackProps{Gap}) explicitly as "the single source of truth for vertical rhythm — replacing the repeated space-y-4 / space-y-6 strings scattered across consumer pages" (ADR-0016). Using the component instead of raw classes is the library's own stated design philosophy.

Recommendation Replace <div class="mt-6 space-y-6"> with layout.Stack(layout.StackProps{Gap: layout.StackGapLG}). 
// Before: raw Tailwind classes
<div class="mt-6 space-y-6">
    @display.Card(...) { ... }
    @display.Card(...) { ... }
</div>

// After: library component with typed gap
@layout.Stack(layout.StackProps{Gap: layout.StackGapLG}) {
    @display.Card(...) { ... }
    @display.Card(...) { ... }
}
Missed Opportunity · Medium-High impact

StatCard Trend, Icon, and Change fields unused

view.templ:39-50 · only Value and Label set on all 3 StatCards

StatCardProps has 4 unused fields: Trend (TrendUp/Down/Warn/None with arrow indicator), Change (delta text like "+12ms"), Icon (leading icon tile, e.g. icons.Clock), and Href (clickable drill-down). For a health dashboard, these fields are high-value: the Latency card could show TrendUp when latency is rising, the Uptime card could use icons.Clock, and the Version card could use icons.Tag. The trend indicator gives operators at-a-glance direction without reading numbers.

Recommendation Populate Icon on all StatCards, Trend on the Latency card (requires tracking previous latency), and Change for delta display. 
// Before: bare stat cards
@display.StatCard(display.StatCardProps{
    Value: fmt.Sprintf("%dms", data.LatencyMs),
    Label: "Check Latency",
})

// After: enriched with icon and trend
@display.StatCard(display.StatCardProps{
    Value:  fmt.Sprintf("%dms", data.LatencyMs),
    Label:  "Check Latency",
    Icon:   icons.Clock,
    Trend:  display.TrendUp,   // arrow indicator when latency rises
    Change: "+5ms",        // delta from last check
})
Missed Opportunity · Medium impact

display.CollapsibleSection for healthy service groups

view.templ:107-118 · all groups rendered as flat Cards

Systems with 20+ healthy services clutter the dashboard with a long "Healthy Services" table. display.CollapsibleSection (native <details>/<summary>) could collapse the healthy group by default, keeping only failing and warning groups expanded. This is a standard status-page UX pattern — operators care about what's broken, not what's healthy. The component supports Open (default expanded/collapsed) and StorageKey (persists preference in localStorage).

Recommendation Wrap the "Healthy Services" group in a CollapsibleSection with Open: false by default. Keep failing/warning groups as regular Cards (always expanded).
Missed Opportunity · Medium impact

icons package — 102 icons, zero used

Not imported anywhere · icons.Icon, icons.Name available

The icons package (102 SVG icons, currentColor themed) is never imported. Icons would enhance: StatCards (via the Icon field), EmptyState (via the Icon field), and could replace text labels in the status table. Relevant icons for a health dashboard: icons.CheckCircle (pass), icons.ExclamationTriangle (warn), icons.XCircle (fail), icons.Clock (uptime/latency), icons.Tag (version), icons.Server (services), icons.Heart (health). The feedback.Alert component already uses icons internally — this is about adding icons to the dashboard's own components.

Recommendation Import github.com/larsartmann/templ-components/icons and populate Icon fields on StatCards and EmptyState.
Missed Opportunity · Medium impact

No loading state — SkeletonCardGrid, Spinner, datastar.Indicator

view.templ · health region empty until first SSE patch arrives

On initial page load, the health region renders real data immediately (from CachedResponse), but if the probe hasn't run yet or the SSE connection is reconnecting, the user sees a bare "No registered services" empty state or stale data with no loading indicator. templ-components offers three loading-state components: feedback.SkeletonCardGrid (pulsing placeholder cards), feedback.Spinner (animated SVG), and datastar.Indicator (signal-based show/hide during Datastar requests). The initial dashboardContent could show a skeleton grid that gets replaced by real data on the first SSE patch.

Recommendation Add a datastar.Indicator inside the LiveRegion that shows a Spinner during SSE reconnection, and consider a feedback.SkeletonCardGrid for the initial render when the probe has no cached data.
Missed Opportunity · Medium impact

display.RelativeTime — no "last updated" timestamp

Not used · display.RelativeTime(RelativeTimeProps{Time, AutoRefresh}) available

The dashboard updates in real-time but never tells the operator when the last check ran. On a monitoring wall display, a stale "Last updated: 5 minutes ago" is the #1 signal that SSE has silently disconnected. display.RelativeTime renders a <time> element with a server-rendered relative string ("2 seconds ago") that auto-refreshes every 30 seconds via Intl.RelativeTimeFormat. This requires tracking a timestamp in the viewModel (the health Response doesn't include one, but the dashboard can stamp time.Now() when CachedResponse() is read).

Recommendation Add a LastChecked time.Time field to viewModel, stamp it in buildViewModel, and render display.RelativeTime in the header or footer of the dashboard.
Missed Opportunity · Low-Medium impact

errorpage package — plain-text error on render failure

dashboard.go:179 · http.Error(w, "dashboard: failed to render page", 500)

When View(data).Render() fails, the dashboard returns a plain-text HTTP error. templ-components ships a full errorpage package with ErrorPage (branded full-page error with What/Why/Fix/WayOut), NotFound404, ErrorHandler (HTTP handler), and pre-built builders (NotFound, InternalError, ServiceUnavailable). Using errorpage.ErrorHandler or at least errorpage.InternalError() would give a branded, consistent error experience matching the dashboard's visual language.

Recommendation Replace http.Error calls with errorpage.WriteError or render an errorpage.ErrorPage for branded error pages.

Partially Used · Medium impact

Badge Dot indicator not set

status.go:182-187 · BadgeProps{Text, Type} — Dot field omitted

BadgeProps.Dot renders a small colored dot before the badge text (e.g. • pass, • fail). This is the standard visual pattern for status indicators — the colored dot is instantly scannable even before reading the text. StatusBadge (which the library uses internally) always sets Dot: true. The dashboard's explicit Badge usage omits it. Adding Dot: true is a one-field change with immediate visual benefit.

Recommendation Add Dot: true to badgeForStatus in status.go. 
// Before: text-only badge
func badgeForStatus(s health.Status) display.BadgeProps {
    return display.BadgeProps{
        Text: string(s),
        Type: mapStatusToBadge(s),
    }
}

// After: with dot indicator
func badgeForStatus(s health.Status) display.BadgeProps {
    return display.BadgeProps{
        Text: string(s),
        Type: mapStatusToBadge(s),
        Dot:  true,   // colored status dot
    }
}
Partially Used · Low-Medium impact

feedback.Alert Message field unused

view.templ:97-100 · only Title set, Message empty

AlertProps has a Message field for secondary detail text rendered below the title. The dashboard only sets Title (e.g. "Unhealthy — Critical Failures"). The health Response has rich data that could populate Message: a count of failing services ("3 of 12 services failing"), the names of failing services, or the shutdown drain message. This makes the status banner more actionable without requiring operators to scan the table.

Recommendation Build a summary message in buildViewModel (e.g. "3 of 12 services failing") and pass it as Message on the Alert.
Partially Used · Low impact

feedback.Alert Dismissible not offered

view.templ:97-100 · Dismissible defaults to false

AlertProps.Dismissible adds a close button that dismisses the banner via utils.DismissScript() (CSP-safe, nonce-gated). On a monitoring dashboard, operators may want to dismiss the overall status banner to focus on individual check tables — especially when the status is "Degraded" and they've already acknowledged it. Currently not offered. Note: the banner is inside the LiveRegion, so SSE patches would re-render it; dismissibility works best when the Alert is outside the patched region.

Recommendation Consider moving the Alert outside the patched region and enabling Dismissible: true, or leave as-is if the banner should always be visible.
Partially Used · Low impact

SimpleEmptyState instead of full EmptyState

view.templ:104 · display.SimpleEmptyState("No registered services")

The dashboard uses SimpleEmptyState (text-only) for the "no services" case. The full display.EmptyState supports Icon (e.g. icons.ServerStack), Description (longer help text), and ActionText/ActionHref (a "Add a service" link). For a dashboard, an icon + description ("No health checks have been registered. Add services to your Probe to see them here.") would be more polished and helpful than bare text.

Recommendation Replace SimpleEmptyState with EmptyState with an appropriate icon and description.
Partially Used · Low impact

Card Footer slot unused for group counts

view.templ:108-117 · only Title and Padding set on check group Cards

CardProps has a Footer slot (renders below the card body) and a Subtitle field. The check group cards only set Title (e.g. "Critical Failures") and Padding. The Subtitle could show the severity, and the Footer could show "N of M services in this group" or a link to filter the table.

Recommendation Add Subtitle with severity text or use Footer for per-group service counts.

07Conclusion

go-health-dashboard uses templ-components correctly but not superbly. The core architecture — Datastar SSE, correct component choices, non-deprecated types, CSP nonce propagation — is exemplary. But the dashboard treats the library as a component shelf rather than a design system: it hand-rolls a page header that display.PageHeader provides, uses raw Tailwind classes instead of layout.Stack, and leaves the icons package entirely untouched. The single highest-leverage next step is adopting the 6 quick wins (PageHeader, Stack, Badge Dot, Alert Message, StatCard Icon, CollapsibleSection) — all are drop-in or near-drop-in, zero new dependencies, and would transform the dashboard from "functional" to "polished" in under an hour of work.
