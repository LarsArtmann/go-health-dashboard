00Summary

Yes — the integration architecture is the best imaginable shape for Go; the execution had one real hole, now closed. The seam is a five-method consumer-side structural interface (Prober), which is exactly what the Go community prescribes: the consumer defines what it needs, the provider satisfies it implicitly, and source compatibility is proven by an untouched test suite plus a stub-prober test. The aggregate pivot (v0.5.0) composed instead of competed. The audit found the shape right and the execution one bug short of ideal: the dashboard marshaled the raw cached snapshot while go-health deliberately sanitizes invalid UTF-8 at its own write seams — the dashboard bypassed that protection on every one of its five write paths.

The bottom line Architecture: best imaginable (consumer-side interface, one-snapshot choke point, zero extra dependencies). Execution: one genuine bug (invalid UTF-8 leaked into jsonv2 JSON output) — found by this audit, fixed at the single choke point, and the regression test was proven to fail without the fix. What remains are three upstream asks for go-health, not dashboard defects.

◆What's already excellent

+
Consumer-side structural Prober interface (dashboard.go:22-37) Five methods, defined on the consumer side per Go convention. *health.Probe and *aggregate.Aggregate satisfy it implicitly; the entire pre-existing suite passed untouched when the interface landed, and TestNew_AcceptsCustomProber pins third-party implementability.
+
One zero-cost snapshot feeds everything CachedResponse() is a lock-free atomic read; the dashboard funnels it through a single choke point (currentResponse, dashboard.go:130) so the HTML view, JSON response, metrics, trend samples, change-detection fingerprints, and webhook payloads all share one consistent snapshot per tick.
+
Error-surface opacity by design The Prober deliberately excludes go-health's error plumbing (ErrProbeUnhealthy, ErrPanicDuringHealthCheck, evaluation hooks). The dashboard cannot leak probe internals, and probe lifecycle errors stay probe-side — a renderer should not re-implement a health-checker.
+
Aggregate composition, end-to-end tested The v0.5.0 "integration over federation" pivot: aggregate.New + namespaced source/check keys + worst-of status, rendered natively, verified by an injector-to-HTML e2e test (integration_test.go) and documented in README + cookbook.
+
Zero-dependency discipline held on both sides The dashboard hand-rolled Prometheus exposition and the token bucket rather than growing its dependency tree; go-health keeps samber/do as its single dependency and the dashboard adds nothing beyond it.

01Findings

Found & fixed today · High impact

Raw snapshot marshaled: invalid UTF-8 leaked past go-health's write-seam protection

handlers.go:94-110 (serveJSON) · webhook.go:123-175 (buildPayload + jsonv2 marshal) · fixed at dashboard.go:130 (currentResponse)

go-health exports SanitizeResponse and applies it in its own handlers explicitly so served bytes stay valid under both encoding/json v1 and v2 semantics for any input (handlers.go:203-220 upstream). The dashboard bypassed it: serveJSON and the webhook payload marshaled the raw CachedResponse() under GOEXPERIMENT=jsonv2. A service-supplied check error containing invalid UTF-8 (raw network garbage is a realistic error payload) produced invalid output bytes. 

// before — raw snapshot reaches five write seams
func (d *Dashboard) currentResponse() health.Response {
    return d.probe.CachedResponse()
}

// after — one choke point sanitizes JSON, webhook, SSE, metrics, CSV
func (d *Dashboard) currentResponse() health.Response {
    return health.SanitizeResponse(d.probe.CachedResponse())
}
Fixed & proven TestJSON_SanitizesInvalidUTF8FromStubProber feeds ÿþ through a stub prober and asserts the served JSON is valid UTF-8, contains U+FFFD, and round-trips. The test was run against the unfixed code and failed, then passed after the one-line fix.
Found & fixed today · Medium impact

NewWithHealthCheck (no-injector path) existed undocumented

go-health accessors.go:34 (v0.1.2) · dashboard README "Why a Separate Repo?"

go-health v0.1.2 ships NewWithHealthCheck(fn HealthCheckFunc, opts...): a full probe built from a plain function, no samber/do injector involved. The dashboard's README framing ("go-health already requires a samber/do injector") undersold this path to non-do applications.

Fixed README now documents the no-do path (NewWithHealthCheck + dashboard.New + Start/Shutdown; only Register needs an injector), and AGENTS.md's go-health notes carry the accessor family.
Upstream ask · Medium impact

StartupComplete() exists on both implementations but not on Prober

go-health probe.go & aggregate · dashboard.go:22-37

Both *Probe and *Aggregate expose StartupComplete(), but the dashboard's interface omits it — so the UI cannot distinguish "starting up" from "pass". Keeping it off is deliberate right-sizing (adding a method breaks external implementers); the payoff would be a startup-aware banner or metric.

Routed ROADMAP candidate; needs a conscious interface-evolution decision (add now while the interface is one release old, or never).
Upstream gap · Medium impact

Aggregate does not participate in samber/do lifecycle cascades

go-health aggregate package (v0.1.2 surface)

*Probe implements do.HealthcheckerWithContext and do.Shutdowner; *Aggregate implements neither, so a registered aggregate is invisible to container-wide do.HealthCheck/do.Shutdown cascades even though it merges probes that do participate.

Ask File upstream: give *Aggregate the same lifecycle interfaces (AND-of-sources healthcheck; shutdown that marks every source). Nothing to change dashboard-side.
Upstream ask · Low impact

Status severity ordering is re-encoded by every consumer

go-health types.go (plain string type) · dashboard trend values + metrics statusValue · aggregate worstOf

Status ships three constants and no ordering. The aggregate's unexported worstOf, the dashboard's trend values (pass=1/warn=0.5/fail=0), and the metrics mapping (2/1/0/−1) each re-encode severity privately. An exported Status.Rank() or Compare in go-health would give the three consumers one truth.

Nice to have · Low impact

Cookbook could recommend probe-side option combos; InstanceID is UI-invisible

go-health probe options · docs/integrations.md · view StatCards

WithGETOnly, WithAllowedMethods, WithLiveThrottle, WithEvaluationHook, WithHealthRecorder, and WithInstanceID are all relevant to dashboard deployments but appear in no recipe. The UI renders Version/Uptime StatCards but ignores Response.InstanceID — and aggregate pages show empty scalars entirely (a known open question from the v0.5.0 report).

02Target state (reached today, minus upstream asks)

// The seam, as of this audit:
type Prober interface {            // consumer-side, five methods, stable
    CachedResponse() health.Response
    RefreshInterval() time.Duration
    LivenessHandler() http.HandlerFunc
    ReadinessHandler() http.HandlerFunc
    StartupHandler() http.HandlerFunc
}

func (d *Dashboard) currentResponse() health.Response {
    return health.SanitizeResponse(d.probe.CachedResponse()) // single choke point
}
This is the target Interface unchanged (right-sized); sanitization centralized; the aggregate renders natively; the no-do path is documented. What remains lives in go-health: aggregate lifecycle interfaces, an exported severity ordering, and a decision on StartupComplete in Prober.
