00Summary

go-health-dashboard is go-health's richest consumer: it renders the probe's cached view over Datastar SSE, forwards every JSON probe handler, and pins upstream capabilities with tests. This audit walked go-health's entire public surface — root package, aggregate, federation, and the checks batteries — at the pinned v0.5.1 and compared each capability against every reference in this repository. The core consumption is exemplary; the gaps cluster in the two consumer binaries (example, health-hub) and two design seams, and nothing is misused.

The bottom line The library's core is fully leveraged, but its two newest observation seams are not. WithEvaluationHook — the probe-cadence observation seam — is unused, so the trend ring and evidence log are blind to flaps that start and clear between two push ticks. And the two-phase drain (WithShutdownGracePeriod / MarkShuttingDown) is unused, so both binaries keep reporting ready while the HTTP server is already draining. Both fixes are small; the hook needs one design decision first because the dashboard receives an already-constructed prober.

01Capability gaps, ordered by impact

Each card grades one go-health capability against this repository's actual usage. Statuses: Missed Opportunity (never touched), Partially Used (a stronger built-in path exists or the wiring is half-done), Fully Leveraged (covered in the strengths section). Zero capabilities graded as misused.

Missed Opportunity · High impact

WithEvaluationHook is unused — trend and evidence are blind between push ticks

go-health README "Observability" + docs/panic-recovery-design.md · 0 references in this repo · observation points: pusher.go tick loop, history.go, evidence.go

The hook fires synchronously after every probe evaluation (probe cadence = WithRefreshInterval, default 1s) with a defensive copy of the classified response, and — since v0.5.1 — a panicking hook is recovered into a visible non-critical "evaluation-hook" warn row. go-health documents it as "the seam for metrics and alerting ... without polling". This repo's trend ring and evidence log instead sample only inside the pusher tick, so a flap that starts and clears between two pushes never deviates, never enters the evidence strip, and never plots on the timeline — precisely the health-washing window the evidence strip exists to close. Constraint: the hook attaches at probe construction, and the dashboard receives an already-built Prober, so the library cannot register it; adoption needs a small ingest API plus consumer wiring. 

// Today: observation cadence == push cadence
for {
    select {
    case <-ticker.C: // PushInterval
        resp := dash.currentResponse()
        ring.record(resp) // trend + evidence sampled here, and only here
    ...
}

// Target: probe cadence feeds the ring, push stays a render cadence
probe := health.NewChecks(demoChecks,
    health.WithEvaluationHook(func(r health.Response) {
        dash.Observe(r) // new: WithEvaluationSink — ring + evidence see every evaluation
    }))
Recommendation Add WithEvaluationSink(func(health.Response)) to the dashboard (ring + evidence ingest, reusing the tick-path recorders), wire the hook in example and hub, and document the consumer-side pattern for external users. Note federation has no hook — its observation happens on the remotes.
Missed Opportunity · High impact

Two-phase drain unused — readiness reports 200 while the HTTP server is draining

example/main.go:112-121 · cmd/health-hub/main.go:175,206-208 · go-health: WithShutdownGracePeriod, MarkShuttingDown (0 references here)

go-health ships the exact primitive for graceful drains: WithShutdownGracePeriod(d) makes Probe.Shutdown first mark the probe draining — readiness flips to 503 while the refresh loop keeps serving fresh 503s for the window — and MarkShuttingDown is the manual two-phase path. Both binaries do the opposite: the HTTP server stops accepting and waits out in-flight requests while the probe still reports ready, so a load balancer polling /readyz keeps routing traffic into a closing process for the entire drain window. The dashboard already models the pattern for its own surface (WithShutdownDrain drains SSE before the broadcaster closes) — the probe side is the missing half. 

<-ctx.Done()
probe.MarkShuttingDown() // readiness -> 503 immediately

drainCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
server.Shutdown(drainCtx) // LBs observed 503s throughout the drain
probe.Shutdown()          // then stop the refresh loop
Recommendation In example and health-hub, mark the probe (or rely on a WithShutdownGracePeriod) BEFORE server.Shutdown, so readiness leads the drain instead of trailing it. One-line reorder in each binary's shutdown path.
Partially Used · Design decision needed

The probe's roll-up verdict never reaches the samber/do health cascade

dashboard.go:242-265 (HealthCheck reports pusher state only) · go-health Probe.HealthCheck wraps ErrProbeUnhealthy — 0 references here

go-health gives the probe its own cascade verdict: Probe.HealthCheck implements do.HealthcheckerWithContext and wraps ErrProbeUnhealthy when the cached roll-up is fail. When a consumer registers the dashboard via dashboard.Register, the cascade only hears the dashboard's pusher verdict (not started / shut down / stale). The example's probes are standalone (never registered as do services), so a fully failing fleet still passes container-wide health checks. The two verdicts are genuinely different questions — "is the real-time surface alive" vs "is the fleet healthy" — so this is a semantics decision, not a bug. 

// Optional-capability pattern already proven by Healthzer (dashboard.go:43-54)
type Healthchecker interface { // do.HealthcheckerWithContext shape
    HealthCheck(ctx context.Context) error
}

func (d *Dashboard) HealthCheck(ctx context.Context) error {
    if err := d.pusherVerdict(); err != nil {
        return err
    }
    if hc, ok := d.probe.(Healthchecker); ok {
        return hc.HealthCheck(ctx) // ErrProbeUnhealthy on fail
    }
    return nil
}
Recommendation Generalize the Healthzer pattern: if the prober implements the do.HealthcheckerWithContext shape, Register forwards its verdict into the cascade (or document that consumers should register the probe separately). Decide the semantics first: federation fail-over staging may WANT the cascade to stay pusher-scoped.
Missed Opportunity · Medium impact

The checks batteries (v0.5.0) have zero adoption — the demo fabricates every state it shows

go-health/checks: Disk, Memory, HTTP, Database · 0 references in this repo · example/main.go:134-152 mocks all checks

v0.5.0 shipped batteries-included CheckFunc-compatible probes with zero dependencies beyond the stdlib, warn-by-default criticality for resource checks (a full disk should alert, not restart the pod — docs/batteries-ownership-decision.md). The example instead scripts its failure states (flapping redis, always-failing exporter), so screenshots and live demos show synthetic data where real moving data is one import away. 

probe := health.NewChecks(map[string]health.CheckFunc{
    "postgres":        new(alwaysHealthy).HealthCheck,
    "disk-headroom":   checks.Disk("/", 5<<30),   // warn-by-default
    "memory-pressure": checks.Memory(1<<30),
}, health.WithCriticalServices("postgres"))
Recommendation Add two battery rows (Disk, Memory) to the example's default probe — real states, real warn-by-default semantics, and the demo stops lying about where its data comes from.
Partially Used · Render side done, producer side absent

health.Off is rendered but never produced — the off path ships unexercised in its own consumer

Rendering: status.go neutral badge, evidence.go exclusion, v0.5.1 pin · Production: health.Off/OffError has 0 call sites here

v0.5.1's headline feature expresses a deliberately unconfigured dependency as a visible row carrying its enable recipe. This repo did the harder half — rendering, roll-up exclusion, evidence-universe exclusion, problem-count exclusion — but nothing in the repository ever returns health.Off, so screenshots, browser tests, and live demos never exercise the state. One line in the example closes the gap. 

"analytics": func(_ context.Context) error {
    return health.Off("not configured: set DEMO_ANALYTICS_URL to enable")
},
Recommendation Add one off row to the example's default probe and refresh the README screenshot — the off badge, its tooltip, and its absence from the evidence strip get exercised on every demo run.
Missed Opportunity · Low effort

health.VersionHandler unused — the build stamp lives in logs, not on an endpoint

example/main.go:90-95 and cmd/health-hub/main.go:181-188 log the version · health.VersionHandler (v0.5.0): 0 references

Both binaries print the version into startup logs and stamp it into health payloads via WithVersion, but neither serves the dedicated identity endpoint the library ships pre-marshaled and GET-guarded (405 + Allow on anything else, unaffected by shutdown). It answers "which build am I talking to?" for scrapers and operators without grepping logs. 

mux.HandleFunc("GET /version", health.VersionHandler(version.Version))
Recommendation Wire /version in example and health-hub; consider a Routes opt-in if the dashboard should own it (identity, not health — keep it out of the probe route set by default).
Partially Used · Forwarding complete, never configured

Routes.Healthz is never turned on — the load-balancer story is only exercised by unit tests

handlers.go:249-256 registers it when set · routes.go:38 defaults to "" · example and hub never set Routes

The Healthz forwarding machinery is complete and pinned by tests (aggregate forwards it — dashboard_test.go:1132; federation deliberately does not — federation_test.go:195), but no in-repo deployment ever configures the route, so the combined-traffic endpoint ("should traffic be routed here?") exists only in unit tests. The example's single and aggregate modes can flip one option; the hub deliberately cannot — federation.Prober has no Healthz by upstream design, so the hub has no single-endpoint LB answer today.

Recommendation Demo Routes.Healthz in the example (one WithRoutes entry), and note for hub operators that the LB story needs an aggregate or probe-backed deployment — or raise the federation.Healthz gap upstream.
Missed Opportunity · Blocked on upstream release

aggregate.SourceStatuses (unreleased) — per-source roll-ups without refolding namespaced keys

go-health unreleased changelog + aggregate.go:170-177 · go.mod pins v0.5.1

One map[string]health.Status entry per source, one atomic cache load per source, no evaluation, no wire impact — it answers "is source api healthy overall?" without folding source/check keys. The hub's per-remote cards currently re-derive exactly this by grouping namespaced checks. Ride the v0.6 bump: the same train carries aggregate.New's joined invalid-source errors and the never-started grace-window fix.

Recommendation When v0.6 tags: bump, then render per-source status from SourceStatuses in the hub's stat cards and add a pin to scripts/check-ui-pins.sh's sibling guard.
Partially Used · Niche

federation.WithClient — the hub has no TLS/proxy transport knob

cmd/health-hub/main.go:151 uses only WithTimeout · WithClient: 0 references

federation.New accepts a custom *http.Client for transport pooling, TLS, or proxying, but the hub's HEALTH_HUB_* environment has no surface for it — a hub that needs a custom CA pool or an egress proxy cannot get one without a code change. Almost certainly fine for the LAN topology the hub targets; worth one env knob if federating across trust boundaries ever becomes real.

Partially Used · Narrow window

AwaitReady unused — binaries serve before the first observation

go-health Probe.AwaitReady (50ms polling, ctx-bounded) · 0 references here

Cached-mode probes pre-populate their cache inside Start, so the window is small — but example and hub still begin serving before the first refresh/fetch completes, and the hub's first seconds render against an empty federation view. One AwaitReady(ctx) before ListenAndServe closes the window; the direct accessors (Ready/Status/Alive) remain deliberately bypassed — the dashboard reads CachedResponse so view, metrics, and change detection share one snapshot.
